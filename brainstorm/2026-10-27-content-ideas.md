## 1. 既存 2 作から読み取った「Deep Cuts の型」と伸びしろ

### 現在の型

| 要素 | 内容 |
| --- | --- |
| 単位 | 1 サービス = 1 リポジトリ（本リポジトリにサブモジュールとして集約） |
| 解説 | Qiita 記事（前提知識から解説） |
| ハンズオン | CloudShell で `setup.sh` → コンソール操作 → `cleanup.sh`。本質でない準備はスクリプト化 |
| 配慮 | 放置コストの明示、後片付けの徹底、Mermaid による構成図 |

「手順通りに進めれば誰でも再現できる」ことへのこだわりは強みです。この型はそのまま残しつつ、次の 3 点を伸ばす余地があると考えます。

### 伸びしろ

1. **「サービス紹介」から「問い」へ**
   Local Zones 回の「ホノルルから測ると本当に速いのか」は、すでに**測定で問いに答える**構成になっています。これを全面に出し、「東京-大阪間で RPO=0 にすると書き込みは何 ms 遅くなるのか」のように、**答えがまだ公開されていない問いを立てて実測で答える**ことが、thought leadership の源泉になります。
2. **「1 サービス縛り」を外す**
   比較（Versus）、論文の再現（Cover）、組み合わせ（Mixtape）、終了したサービスの検証（Out of Print）など、サービス単位では書けない切り口に価値があります。
3. **鮮度の管理を仕組みにする**
   ニッチなサービスほど変化が速く、終了リスクもあります。後述の Radar で見ると、**AWS SDK からのサービス削除は 2023 年まで年 0〜2 件だったのが、2024 年 8 件、2025 年 15 件、2026 年（10 月まで）9 件**と急増しています。Deep Cuts が紹介したサービスが終了する事態は十分ありえるので、「最終検証日」「ライフサイクル監視」「ハンズオンの定期実行」を仕組みとして持つべきです（§5）。

## 2. 提案：Deep Cuts を「レーベル」にする

Deep Cuts（＝アルバムの隠れた名曲）という名前は音楽の比喩なので、コンテンツの種類も音楽用語で揃えると、シリーズとしての一貫性と「次は何が出るか」の期待感を作れます。

| レーベル | 中身 | 例（本メモ内のアイデア） |
| --- | --- | --- |
| **Deep Cut** | 現行の型。ニッチなサービスの解説＋ハンズオン | Ground Station、HealthImaging、Mail Manager |
| **New Release（新譜）** | 出たばかりで日本語情報がほぼないサービスを最速で検証 | Lambda MicroVMs、S3 Files、IAM Toolbox |
| **B-Side** | 有名サービスの、知られていない機能・仕様 | EC2 の見えない帯域・PPS 制限、S3 条件付き書き込み |
| **Remix** | 本来の用途と違う使い方で、仕組みの理解を深める | GameLift FlexMatch で勉強会のチーム分け |
| **Cover** | 有名なシステムや論文を AWS の部品で再現する | Google Spanner の TrueTime を Amazon Time Sync で作る |
| **Live** | 実測が主役。生データも公開する | 東京-大阪 RPO=0 のレイテンシ税 |
| **Liner Notes** | サービスの裏にある論文・内部設計を読み解く | Firecracker、SRD、Zelkova |
| **Out of Print（廃盤）** | 終了したサービスから設計と技術選定の教訓を引き出す | QLDB 亡き後の改ざん検知台帳 |
| **Red vs Blue** | 自分のアカウント内で攻撃を再現し、防御サービスで止める | DNS トンネリング vs DNS Firewall |
| **Mixtape** | 複数の Deep Cuts を組み合わせた 1 つのアーキテクチャ | AI が 24 時間運営するテレビ局 |

各コンテンツの冒頭に「レーベル」「ぶっ飛び度」「ハンズオン費用」「所要時間」「最終検証日」を載せる「ジャケット」（メタデータ欄）を付けることも提案します。

## 3. Deep Cuts Radar：SDK の履歴からわかったこと

題材探しのために、AWS SDK for Python（botocore）の Git 履歴から、全サービスの API モデルの追加・変更・削除を集計しました（スクリプトと結果は [`radar-poc/`](./radar-poc/)）。これ自体が 1 本のコンテンツになる手応えがあります（アイデア K-1）。

### 3-1. 2024 年から AWS は「剪定期」に入った

| 年 | SDK に追加されたサービス | SDK から削除されたサービス |
| --- | --- | --- |
| 2015〜2019 | 219 | 0 |
| 2020〜2023 | 162 | 5 |
| 2024 | 37 | 8 |
| 2025 | 25 | 15 |
| 2026（10 月まで） | 29 | 9 |

※ 2015 年の数字（62）は、botocore が現行のディレクトリ構成になった時点で既に存在したサービスを含みます。2023 年以前の削除は、名称変更（例：`redshiftserverless` → `redshift-serverless`）や Macie Classic の整理が中心でした。

2026 年に SDK から消えたもの：Evidently、IoT Analytics（2 月）、IoT Events、Panorama、SimSpace Weaver（6 月）、FinSpace、Telco Network Builder（10 月）。
2024 年以降に削除されたサービスの「SDK 上の寿命」（API モデル追加から削除まで）は中央値で約 67 か月（n=32、サブ API を個別に数えた値）。最短は IoT RoboRunner（約 16 か月）と、Mainframe Modernization の Application Testing（`apptest`、2024-06 → 2025-10、約 16 か月）でした。
一方で、2007 年からある SimpleDB には 2026 年 3 月に `simpledbv2` が追加されましたが、その API は `StartDomainExport` / `GetExport` / `ListExports` の 3 つだけで、**データを外へ持ち出すための API**です。

## 4. アイデア全集

凡例：🌶️ = ぶっ飛び度（🌶️〜🌶️🌶️🌶️🌶️🌶️）、💴 = ハンズオン費用の目安（💴 ≒ 数十円〜数百円、💴💴 ≒ 数百円〜数千円、💴💴💴 ≒ 数千円以上、または要見積もり）、〔要確認〕= 執筆前に一次情報で再確認が必要な点。

### アルバム A：New Release（2025 年後半〜2026 年の新サービス）

日本語の解説がほぼ存在しない今が、Deep Cuts が「最初の深掘り」を出せるチャンスです。

#### A-1. メモリごと眠らせる serverless — Lambda MicroVMs ／ `New Release` `Liner Notes` 🌶️🌶️🌶️ 💴

- **主役**：Lambda MicroVMs（2026-06-22 発表。東京は初日からの提供リージョン）
- **フック**：Firecracker の microVM を API で `RunMicrovm` し、`SuspendMicrovm` で**メモリとディスクの状態を保ったまま停止**、`ResumeMicrovm`（またはトラフィック到着時の自動レジューム）で再開できる。microVM ごとに専用 HTTPS エンドポイント（HTTP/2・gRPC・WebSocket）が付く。用途として AI が生成したコードの隔離実行が想定されている。
- **ハンズオン案**：Python REPL を載せた MicroVM イメージを作り、変数を定義 → サスペンド → レジュームして**変数が生きている**ことを確認。レジューム時間を計測する。`SHELL_INGRESS` 接続でのシェル接続も試す。
- **Liner Notes**：Firecracker 論文（NSDI 2020）の「最小のデバイスモデル」「jailer」、SnapStart と共通するスナップショット復元の仕組みを読み解く。2026-02 に C8i / M8i / R8i で**ネストされた仮想化**が GA になったので、ベアメタルなしで Firecracker そのものを動かし、マネージド版と比べる回も作れる。
- **答えのない問い**：Lambda は 2025〜2026 年に、テナント分離モード（2025-11）、Managed Instances（2025-12）、Durable Functions（2025-12、最長 1 年のワークフロー）、MicroVMs（2026-06）、Web Functions（2026-10）へと分化し、従来の関数は「Lambda Event Functions」と呼ばれるようになった。**「サーバーレス」の境界はどこに引き直されるのか**。各形態の地図を描き、使い分けの判断基準を提案する。
- **注意**：料金体系の詳細、Arm64 のみか、最大サイズ（16 vCPU / 32 GB とする第三者情報あり）、サスペンド可能時間の上限（8 時間とする情報あり）〔要確認〕。

#### A-2. 「待ち時間に課金しない Lambda」の経済学 — Lambda Web Functions ／ `New Release` `Live` 🌶️🌶️ 💴

- **主役**：Lambda Web Functions（2026-10-12。東京は開始時からの提供リージョン）、Lambda Core のネットワークコネクタ（VPC 接続）
- **フック**：コードが `AWS_LAMBDA_HTTP_ENDPOINT` で待ち受ける普通の HTTP サーバーになり、Express / Hono / React Router がアダプターなしで動く。1 つの実行環境が最大 128 リクエストを同時処理し、**課金はアクティブな CPU 時間（メモリは別建て）**で、DB や下流サービスを待つアイドル CPU 時間には課金されない。開始時点のランタイムは Node.js 24（Arm64）のみ。
- **ハンズオン案**：同じ Hono アプリを「従来の Lambda（Event Functions）＋アダプター」と「Web Functions」で動かし、下流待ちが長い API（例：Bedrock のストリーミング応答を待つ処理）に負荷をかけて、課金対象・同時実行数・レイテンシを比較する。
- **答えのない問い**：生成 AI 呼び出しのように**「待ち」が支配的なワークロード**では、従来の Lambda は待ち時間にも課金されていた。この課金モデルの変化で、Lambda・Fargate・App Runner 系の損益分岐点はどう動くのか。
- **注意**：料金単価の詳細〔要確認〕。

#### A-3. AccessDenied の真犯人を指名する — IAM Toolbox ／ `New Release` `B-Side` 🌶️ 💴

- **主役**：IAM Toolbox の `GetRequestAuthorizationDetails`（2026-08-25 からプレビュー、us-east-1 のみ）、IAM Policy Simulator（2026-07 から SCP の条件も評価）
- **フック**：対応サービスの AccessDenied エラーには認可 ID が含まれ、それを渡すと**リクエストコンテキスト、評価の過程、評価されたポリシー**が返る。詳細は少なくとも 24 時間保持。呼び出しは拒否が起きたのと同じリージョン、同じアカウントまたは組織から行う必要がある。
- **ハンズオン案**：「AccessDenied 図鑑」。ID ベースポリシーの不足、アクセス許可の境界、セッションポリシー、S3 バケットポリシーの明示的 Deny、KMS キーポリシーなど、原因の違う拒否を意図的に起こし、それぞれの評価過程を取得して IAM のポリシー評価ロジックの図と突き合わせる。
- **答えのない問い**：エラーに認可 ID を載せることは、攻撃者に手がかりを与えないのか。**「認可のデバッグ容易性」と「情報の秘匿」のトレードオフ**を AWS はどう設計したのか。
- **注意**：対応サービスの範囲、GA 時期、東京での提供時期〔要確認〕。

#### A-4. AWS サポートにも「令状」を — AWS Support authorization ／ `New Release` 🌶️🌶️🌶️ 💴

- **主役**：AWS Support authorization（SupportAuthZ、API バージョン 2026-06-30）
- **フック**：AWS サポート担当者があなたのリソースに対して行える操作を、**対象リソース・操作・時間枠を指定し、顧客管理の KMS 鍵（ECC_NIST_P384、SIGN_VERIFY）で署名した「サポート許可証（support permit）」**で認可する。担当者からの許可リクエストは一覧・却下でき、許可証の削除で認可を取り消せる。署名は否認防止のため。
- **ハンズオン案**：KMS 鍵の作成と登録（`supportauthz:RegisterKey`）、許可証の発行・一覧・失効までを一通り行い、署名の中身を確認する。
- **答えのない問い**：Nitro System の「AWS のオペレーターもホストにアクセスできない」設計、Nitro Enclaves、そして SupportAuthZ。**「クラウド事業者の人間がどこまで顧客データに触れうるのか」を顧客側が暗号学的に統制する**流れは、ソブリンクラウドの議論にどう効くか（アルバム B と連動）。
- **注意**：許可証が実際に要求されるサポートの範囲（サポートプランとの関係）、料金〔要確認〕。

#### A-5. EventBridge は「ルーター」から「ログ」になった — 新カスタムイベントバス ／ `New Release` `Live` 🌶️🌶️ 💴

- **主役**：Amazon EventBridge の新しいカスタムイベントバス（2026-09-24。従来のバスは「classic」に改名）
- **フック**：イベントを**既定 24 時間、最大 1 年保持**し、新設の Subscriber リソースがフィルタ・変換（JSONata）して配信する。イベントグループ単位の FIFO 配信、CloudEvents 形式、内容または ID ベースの重複排除、任意形式を送れる `PutRawEvents`、RAM によるクロスアカウント共有、イベント数ではなくデータ量（GB）ベースの料金。API は別の名前空間（`eventsv2`、CBOR プロトコル）。
- **ハンズオン案**：イベントソーシングの実験。注文イベントを順序付きで流し続け、**後から追加した Subscriber に過去分をリプレイ**して読み取りモデル（DynamoDB）を再構築する。順序保証と重複排除の挙動も検証する。
- **答えのない問い**：同じ 2026 年に、MSK Express ブローカーがトピックを S3 Tables の Iceberg テーブルとして実体化する機能（07 月）や、Kinesis Data Streams から S3 Tables へ直接届ける機能（08 月）も出た。**「バス」「ストリーム」「テーブル」の境界が溶けたとき**、イベント駆動アーキテクチャの設計原則はどう変わるか。
- **注意**：対応リージョン（開始時 14 リージョン）、料金の詳細〔要確認〕。

#### A-6. S3 Files の上で SQLite と git は正しく動くか — S3 Files ／ `New Release` `B-Side` 🌶️🌶️🌶️ 💴

- **主役**：Amazon S3 Files（2026-04-07）
- **フック**：S3 バケット（またはプレフィックス）を、EFS を土台にした NFS 4.1 / 4.2 のファイルシステムとして EC2・ECS・EKS・Lambda からマウントできる。アクティブなデータは約 1 ms のレイテンシ。S3 との双方向同期と、同期ルール（取り込み・期限切れ）を持つ。

- **答えのない問い**：Mountpoint for Amazon S3、FSx for Lustre の S3 連携、EFS、そして S3 Files。**「オブジェクトかファイルか」という二択は終わるのか**。S3 がストレージの全階層を飲み込む未来の設計指針を考える。
- **注意**：料金体系（32 KB の最小課金単位があるとの第三者報告あり）、ECS の起動タイプごとの対応状況（ドキュメントの版によって記述が異なる）〔要確認〕。

#### A-9. AI クローラーから通行料を取る — AWS WAF の x402 マネタイズ ／ `New Release` `Thought` 🌶️🌶️🌶️🌶️🌶️ 💴

### アルバム B：Trust ― 誰が私のデータに触れられるのか

#### B-1. 管理者にも覗けないシークレットサンタ — Nitro Enclaves ／ `Remix` 🌶️🌶️🌶️🌶️ 💴

- **主役**：AWS Nitro Enclaves、AWS KMS（アテステーションに基づく鍵ポリシー条件）
- **フック**：Enclave は親インスタンスの root からも隔離された環境で、KMS のキーポリシーで「特定の Enclave イメージ（PCR 値）からの要求にだけ復号を許す」ことができる。つまり**運営者自身にも中身が見えない処理**を作れる。
- **ハンズオン案**：参加者の希望を暗号化して集め、Enclave の中でだけ復号・マッチングし、結果は各参加者の公開鍵で暗号化して返す「シークレットサンタ」。発展形として、締切まで誰も入札額を見られない「封印入札オークション」。親インスタンスから覗こうとして失敗するところまで見せる。
- **答えのない問い**：Confidential Computing の定義は、AWS（Nitro System はそもそもオペレーターがアクセスできない設計、という立場）と、他クラウドの TEE 中心の定義とでずれている。**「誰を信頼しなくてよいのか」で整理し直す**と何が見えるか。
- **注意**：Enclave に割り当てる vCPU・メモリの要件があるため、インスタンスサイズに下限がある〔要確認〕。

#### B-2. AWS から他クラウドへ、キーなしで入る — IAM outbound identity federation ／ `B-Side` `Featuring` 🌶️🌶️ 💴

- **主役**：`sts:GetWebIdentityToken`
- **フック**：AWS 上のワークロードが STS から**署名付きの短命な JWT** を取得し、外部サービスがそれを AWS の公開鍵で検証する。アカウント単位で有効化すると専用の発行者（issuer）URL が払い出され、OIDC ディスカバリーのエンドポイントを持つ。このトークンで AWS 自身に `AssumeRoleWithWebIdentity` することはできず、STS のグローバルエンドポイントでは使えない。
- **ハンズオン案**：Lambda から JWT を取得し、Google Cloud の Workload Identity Federation で交換して GCS のオブジェクトを読む。サービスアカウントキーを一切作らずに済むことを確認する。
- **答えのない問い**：OIDC の JWT が事実上「ワークロードのパスポート」になった。**マルチクラウドのゼロトラストは OIDC で完結するのか**、SPIFFE / SPIRE のような仕組みはどこで要るのか。

#### B-3. ハードウェアに縛られた AWS 認証情報 — IAM Roles Anywhere ＋ TPM / YubiKey ／ `B-Side` 🌶️🌶️ 💴

- **主役**：IAM Roles Anywhere、`aws_signing_helper`（PKCS#11・TPM 2.0 の秘密鍵に対応〔対応バージョン要確認〕）
- **フック**：X.509 証明書で一時認証情報を得る Roles Anywhere は、独自の CA 証明書をトラストアンカーにできる。秘密鍵をハードウェアから出さない構成にすれば、**ノート PC のディスクに AWS の秘密が一切残らない**。
- **ハンズオン案**：自前の CA（openssl）で発行した証明書の鍵を YubiKey（PIV）または TPM に格納し、`credential_process` で AWS CLI を使う。鍵を抜いたら何もできないことを確認する。
- **答えのない問い**：人間は Identity Center や `aws login`、ワークロードは IAM ロールと Roles Anywhere。**「長期アクセスキーゼロ」の最後に残るのはどこか**。

#### B-4. 量子コンピュータ時代の暗号を、今測る — PQC on AWS ／ `Live` 🌶️🌶️🌶️ 💴

- **主役**：KMS の ML-DSA 署名鍵、KMS の ML-KEM 鍵（2026-10-26 に `Encapsulate` / `Decapsulate` API が追加）、Private CA の ML-DSA（2025-11）、AWS エンドポイントのハイブリッド PQ TLS、CloudFront / ELB の PQ 対応〔各サービスの対応状況要確認〕
- **フック**：「今盗んで、量子計算機ができたら復号する（Harvest Now, Decrypt Later）」攻撃に対し、AWS はどこまで既に PQ 化しているのか。2026 年 10 月には、HSM に守られた鍵で PQ の鍵カプセル化（KEM）まで API で叩けるようになった。
- **ハンズオン案**：ML-KEM 対応の OpenSSL（3.5 以降）で主要な AWS エンドポイントへ接続し、**どこが `X25519MLKEM768` を交渉するか**を一覧化する。ハンドシェイクのサイズ増とレイテンシ増も測る。KMS の ML-DSA 鍵で署名して手元で検証し、ML-KEM 鍵でカプセル化した共有鍵からファイルを暗号化する。
- **答えのない問い**：日本の組織は**いつ・何から** PQC に移行すべきか。TLS（通信）と署名（長期の真正性）で優先度はどう違うか。

#### B-5. 47 日証明書の時代 — ACM の自動更新はどこまで守ってくれるか ／ `Thought` 🌶️🌶️ 💴

- **主役**：AWS Certificate Manager（エクスポート可能なパブリック証明書、2026-06 の **ACME エンドポイント**）、AWS Private CA
- **フック**：CA/Browser Forum の決定（SC-081）で、パブリック TLS 証明書の最大有効期間は 2026-03-15 から 200 日、2027-03-15 から 100 日、2029-03-15 から 47 日へと段階的に短縮される。ACM が自動更新する証明書はよいが、**ACM の外（アプライアンス・オンプレ・他クラウド）に置いた証明書**が障害の火種になる。そこへ ACM が自前の ACME サーバーを提供し始めた（外部アカウントバインディングの資格情報を IAM ロールに紐付け、certbot などの ACME クライアントから ACM の証明書を取得・更新できる）。
- **ハンズオン案**：オンプレに見立てた EC2 上の nginx で、certbot から ACM の ACME エンドポイントを使って証明書を取得し、自動更新を回す。あわせてアカウント内の証明書（ACM・IAM サーバー証明書・各種カスタムドメイン）を棚卸しし、失効までの日数を EventBridge で監視する。
- **答えのない問い**：証明書の短命化は、セキュリティ向上と引き換えに**運用障害のリスクをどこへ移すのか**。

#### B-6. 改ざんできない台帳を自作する（QLDB 亡き後に） ／ `Out of Print` `Cover` 🌶️🌶️🌶️🌶️ 💴

- **主役**：S3 Object Lock、KMS 署名、（参考）Certificate Transparency の Merkle tree
- **フック**：台帳 DB の Amazon QLDB は 2025 年に提供を終了し、SDK からも削除された（2025-10）。しかし「改ざん検知可能なログ」の需要は消えていない。
- **ハンズオン案**：追記専用ログを S3 に置き、RFC 6962（Certificate Transparency）方式の Merkle tree を構成して、ルートハッシュを定期的に KMS で署名し、Object Lock で保護する。**包含証明と一貫性証明を検証する CLI** まで作る。
- **答えのない問い**：台帳 DB はなぜ定着しなかったのか。**透明性ログ（CT、Sigstore）の思想こそが本質**だったのではないか。
- **注意**：Object Lock のコンプライアンスモードは root でも保持期間中は削除できない。ハンズオンでは保持期間を 1 日などに短く設定し、注意書きを徹底する。

#### B-7. AWS の中の数学 — 自動推論（Automated Reasoning）三部作 ／ `Liner Notes` 🌶️🌶️🌶️🌶️ 💴

- **主役**：IAM Access Analyzer（Zelkova、SMT ソルバー）、VPC Reachability Analyzer（Tiros）、Amazon Bedrock Guardrails の Automated Reasoning checks
- **フック**：AWS はポリシーやネットワーク到達性を、パケットを送らず**論理式に変換して証明**している。同じ技術が生成 AI の回答検証にも使われ始めた。
- **ハンズオン案**：①Access Analyzer のカスタムポリシーチェックを CI に組み込む、②Reachability Analyzer で「なぜ届かないか」を証明させる、③社内規程（例：経費精算規程）から Automated Reasoning のポリシーを作り、LLM の回答を検証する。
- **Automated Reasoning checks の勘所**（2025-08 GA）：規程文書（PDF / TXT、5 MB まで）から AI が型・変数・if-then ルールを抽出して論理式にし、検証時は質問と回答も論理式に翻訳してソルバーで判定する。判定は valid / invalid / satisfiable / impossible / translationAmbiguous などに分かれる。1 ポリシーあたりルール 1,500・変数 600 まで。
- **答えのない問い**：「LLM の幻覚を数学で止める」は本当に可能か。**自然言語を論理式に翻訳する工程自体が LLM に依存する**という自己言及をどう扱うか（判定結果に「翻訳が曖昧」が独立して存在するのが、その答えの一端）。
- **注意**：Automated Reasoning checks は東京リージョンになく（米国・欧州のみ）、2026-09-30 から識別子に Unicode が使えるようになり英語以外のポリシーが作れるとされるが、日本語の規程でどこまで実用になるかは未検証。それ自体が検証テーマになる。

#### B-8. 【ネタ枠】IAM にパズルを解かせる ／ `Remix` 🌶️🌶️🌶️🌶️🌶️ 💴

- **主役**：IAM Access Analyzer のカスタムポリシーチェック（`CheckAccessNotGranted`）
- **フック**：IAM ポリシーは「Allow の論理和」から「Deny の論理和」を引く論理式で、条件キーは AND / OR を持つ。ならば充足可能性問題（SAT）を IAM ポリシーに符号化し、Access Analyzer の自動推論に**「このポリシーはアクセスを許しうるか」を聞けば、パズルが解けるのでは**。
- **構想**：各変数を条件キー（例：`aws:RequestTag/x1` が `"0"` か `"1"`）で表し、節ごとに「その節が偽になる組み合わせ」を Deny する。小さな数独や N-Queens を解かせる。
- **価値**：IAM の評価ロジック（明示的 Deny の優先、条件の AND / OR）と、Zelkova がポリシーを論理式として扱っていることを体感できる。
- **注意**：**実現可能性は PoC が必要**（ポリシーサイズの上限、Access Analyzer が条件をどこまで記号的に扱うか）。失敗しても「なぜできないか」が記事になる。

#### B-9. ランサムウェアからの復旧訓練 — AWS Backup の論理エアギャップボールト ／ `Live` 🌶️🌶️ 💴💴

- **主役**：AWS Backup（論理的にエアギャップされたボールト、復元テスト）、AWS のマルチパーティ承認〔各機能の提供時期・前提条件要確認〕
- **フック**：「バックアップは、復元するまではシュレディンガーの猫」。アカウントごと乗っ取られた想定で、別アカウントから、複数人の承認を経て復元できるか。
- **ハンズオン案**：バックアップ取得 → 元リソース削除（侵害の模擬）→ 復旧用アカウントでの復元 → 復元テストのスケジュール化と RTO の計測。2026-08 に追加された「復旧ポイントへの読み取り専用 S3 アクセスポイント」で、復元せずに中身を確かめる手順も比べる。
- **答えのない問い**：自動化された復元テストは、どこまで「事業継続の保証」になりうるか。

#### B-10. ソブリンクラウドの地図 — AWS の「パーティション」を読み解く ／ `Thought` 🌶️🌶️🌶️

- **主役**：AWS のパーティション（`aws`、`aws-cn`、`aws-us-gov`、各種 ISO、2026-01-15 に GA した AWS European Sovereign Cloud〔パーティション名要確認〕）、日本のガバメントクラウド
- **フック**：ARN の先頭にある `arn:aws:` の `aws` は「パーティション」で、AWS にはそれ以外の「別世界」が複数ある。主権（ソブリン）の議論は、リージョン選択からパーティション分離、運用者の国籍、そして SupportAuthZ のような暗号学的統制まで、**多層の話**だと整理できる。
- **日本の文脈**：デジタル庁の政府共通の生成 AI 基盤「源内」は AWS 上で GenU をベースに構築されていると報じられ、2026 年度のガバメントクラウドには国産のさくらのクラウドも含まれる〔一次情報で要確認〕。
- **答えのない問い**：日本にとっての「ソブリンクラウド」は、どの層までを要求すべきか。

### アルバム C：時間・一貫性・レジリエンス

#### C-1. Google の TrueTime を AWS で作る — Amazon Time Sync Service ＋ ClockBound ／ `Cover` `Live` 🌶️🌶️🌶️🌶️ 💴

- **主役**：Amazon Time Sync Service、2026-06 に登場した EC2 の **precision-time プレイスメントグループ**（PTP ハードウェアクロックとハードウェアによるパケットのタイムスタンプで、マイクロ秒精度の時刻同期）、ClockBound（AWS の OSS。時刻とその誤差範囲を返す）
- **フック**：Spanner の外部一貫性を支える TrueTime は「今は [earliest, latest] のどこか」という**誤差付きの時刻**を返す API。ClockBound も同じ発想で誤差範囲を返す。Aurora DSQL の強い一貫性も精密な時刻同期の上に成り立っている。
- **ハンズオン案**：NTP 同期のみのインスタンスと precision-time プレイスメントグループ内のインスタンスで、ClockBound が返す誤差範囲を 24 時間記録して比べる。誤差範囲を使って「コミット待ち（commit wait）」を実装し、外部一貫性が保たれる様子を可視化する。
- **注意**：precision-time プレイスメントグループに入れられるインスタンスタイプと料金〔要確認〕。
- **答えのない問い**：誤差付き時刻が汎用クラウドのコモディティになった今、**アプリケーション開発者が時刻の不確かさを直接扱う設計**は普及するのか。

#### C-2. 東京-大阪で RPO=0 にすると、書き込みは何 ms 遅くなるのか ／ `Live` 🌶️🌶️ 💴

- **主役**：Aurora DSQL のマルチリージョンクラスター、DynamoDB グローバルテーブルのマルチリージョン強い整合性（MRSC）〔アジアパシフィックで組めるリージョンの組み合わせ要確認〕
- **フック**：「マルチリージョンで強い一貫性」は、物理的には往復遅延の支払いを意味する。公開されている数字は少なく、**日本の 2 リージョンでの実測値**には価値がある。
- **ハンズオン案**：単一リージョン構成と比べた書き込みレイテンシ（p50 / p99）、同一キーへの競合書き込み時の挙動（DSQL の楽観的同時実行制御による競合エラー）、片側リージョン障害の模擬時の振る舞いを比較する。
- **答えのない問い**：PACELC 定理でいう「平常時の L（レイテンシ）と C（一貫性）のトレードオフ」を、日本企業の DR 要件ではどこで線引きすべきか。

#### C-3. S3 is all you need — 条件付き書き込みで分散ロックを作る ／ `B-Side` 🌶️🌶️🌶️ 💴

- **主役**：S3 の条件付き書き込み（`If-None-Match`：2024-08、`If-Match`：2024-11）、バケットポリシーによる条件付き書き込みの強制〔条件キー要確認〕
- **フック**：S3 単体で compare-and-swap ができるようになり、**DynamoDB なしでリーダー選出・分散ロック・WAL** が組める。オブジェクトストレージだけで動く DB やストリーム基盤（S3 ネイティブなアーキテクチャ）という潮流の土台でもある。
- **ハンズオン案**：S3 だけでリーダー選出とリースを実装し、複数プロセスで奪い合わせる。DynamoDB の条件付き書き込みによる実装と、レイテンシ・コスト・故障時の挙動を比較する。
- **答えのない問い**：ステートを S3 に寄せる設計はどこまで広がるか。**「DB を持たないシステム」は運用を本当に軽くするのか**。

#### C-4. 東京が落ちた日の予行演習 — ARC Region switch ／ `Deep Cut` 🌶️🌶️🌶️ 💴💴

- **主役**：Amazon Application Recovery Controller の Region switch（2025-08 GA、直近 12 か月も活発）、AWS Capabilities by Region（2025-11〜）
- **フック**：マルチリージョンのフェイルオーバーを「計画（plan）」として定義し、実行ブロック（Aurora / Neptune のグローバルデータベース、Lambda のイベントソースマッピングの切り替え、Systems Manager など）をオーケストレーションする。2026-09 には切り替え先のクォータが揃っているかを確かめるチェッカーも加わった。
- **日本の文脈**：AWS Capabilities by Region を使った集計では、東京にはあって大阪にはないサービスが 41 あるという報告がある（2026-09 時点、クラスメソッド調べ）。**「大阪に切り替えたら動かないもの」こそが東京 DR の盲点**になる。
- **ハンズオン案**：東京をプライマリ、大阪をセカンダリにした小さな Web アプリで、Region switch の計画を作って切り替え・切り戻しを実行し、各ステップの所要時間を記録する。自分の構成が使うサービス・機能が大阪にあるかを Capabilities by Region で機械的に照合するスクリプトも付ける。
- **答えのない問い**：日本企業の DR 訓練は年 1 回の「儀式」になりがち。**切り替えを日常的に実行できるようにする**には何が要るか。

### アルバム D：ネットワークの物理

#### D-1. 「最大 12.5 Gbps」の本当の意味 — EC2 の見えない制限を踏み抜く ／ `B-Side` `Live` 🌶️🌶️🌶️ 💴

- **主役**：ENA ドライバーの許容量超過メトリクス（帯域・PPS・コネクション追跡・リンクローカル）、リンクローカルサービス（Route 53 Resolver・IMDS・Time Sync）への ENI あたりのパケット数制限〔具体値とメトリクス名要確認〕
- **フック**：「最大 X Gbps」のインスタンスはバースト用のクレジット（トークンバケット）で動いており、持続帯域は別にある。DNS クエリの多いアプリが**リンクローカルの PPS 上限**で謎のタイムアウトを起こすのも定番の落とし穴。どちらもマネジメントコンソールには出てこない。

- **答えのない問い**：クラウドの「スペック表」は何を約束していて、何を約束していないのか。**SLO を設計するときに見るべき本当の数字**はどれか。

- **ハンズオン案**：同一 AZ の 2 台で ENA Express のオン・オフを切り替え、単一フローのスループットとテールレイテンシ（p99.9）を比較する。

### アルバム E：サーバーレスとストレージの B 面

#### E-1. 1 万並列のサーバーレス・スパコン — PyWren の系譜を辿る ／ `Cover` `Live` 🌶️🌶️🌶️🌶️ 💴

- **主役**：AWS Lambda（関数ごとに 10 秒あたり 1,000 同時実行ずつスケール〔要確認〕）、Step Functions の Distributed Map
- **フック**：UC Berkeley の PyWren（SoCC 2017「Occupy the Cloud」）以来、「Lambda を使い捨てのスパコンにする」研究の系譜がある。当時からスケーリング特性も料金も大きく変わった。

- **主役**：Babelfish for Aurora PostgreSQL（SQL Server のワイヤープロトコル TDS と T-SQL を解釈）、Babelfish Compass（互換性評価ツール）
- **ハンズオン案**：SQL Server 向けのサンプルアプリの接続先を Babelfish に変え、どこまでそのまま動くか、どこで止まるかを記録する。

#### I-5. 「自治体の三層分離」とリモートブラウザ分離 — WorkSpaces Secure Browser ／ `Deep Cut` `Thought` 🌶️🌶️ 💴💴

- **主役**：Amazon WorkSpaces Secure Browser（月間アクティブユーザー課金。東京の標準サイズで 1 ユーザー月 $8.50）
- **フック**：日本の自治体ネットワークの「三層分離」で使われてきた画面転送型のインターネット分離は、まさにリモートブラウザ分離（RBI）。クラウドのマネージド RBI で何が置き換えられるかを整理する。コピー・貼り付け・ダウンロード・アップロード・印刷を個別に制御でき、27 カテゴリの Web コンテンツフィルタ（生成 AI のカテゴリもある）、入力データのマスキング、操作ログ（URL 読み込み・クリップボード・ファイル転送など 17 種のイベント）を持つ。動画による録画はない。
- **ハンズオン案**：IAM Identity Center と連携したポータルを作り、「生成 AI サイトへのアップロードだけを禁止する」ような実務的なポリシーを試し、操作ログを確認する。

#### I-6. メールゲートウェイとアーカイブを AWS で — SES Mail Manager ／ `Deep Cut` 🌶️ 💴

- **主役**：Amazon SES Mail Manager（受信エンドポイント、トラフィックポリシー、ルールセット、アーカイブ、アドオン）〔東京リージョン・アドオン提供ベンダー要確認〕
- **ハンズオン案**：自分のドメインの受信メールを Mail Manager で受け、ルールで振り分けとアーカイブを行い、アーカイブを検索・エクスポートする。

#### I-7. INS ネット終了と EDI 移行 — Transfer Family（AS2）／ `Deep Cut` `Thought` 🌶️🌶️ 💴

- **主役**：AWS Transfer Family の AS2、（関連）AWS B2B Data Interchange
- **フック**：NTT の INS ネット（ディジタル通信モード）の終了で、日本の企業間 EDI はインターネット EDI への移行を迫られてきた〔終了・補完策の時期要確認〕。公開予定の B2B Data Interchange を「日本の EDI 事情」から書けば、日本語コンテンツとしての独自性が出る。
- **注意**：B2B Data Interchange は Radar で直近 12 か月の API 変更が 0 件。題材の軸足を Transfer Family 側に置く選択肢も含めて検討したい。

#### I-8. eKYC の顔認証を作る — Rekognition Face Liveness ／ `Deep Cut` 🌶️🌶️ 💴

- **主役**：Amazon Rekognition Face Liveness（東京で利用可、1 回 $0.0195 から。顔の動きと光の変化を使うチャレンジと、動きだけのチャレンジがある）、Amplify UI の Liveness コンポーネント
- **ハンズオン案**：ブラウザで生体検知（なりすまし対策）を行い、身分証の顔写真との照合（CompareFaces）まで実装する。
- **注意**：日本の本人確認の法令（犯罪収益移転防止法の施行規則など）に触れる場合は、一次情報で慎重に確認する。

### アルバム J：お金と地球

#### J-1. どこで動かすのが地球と財布に一番やさしいか ／ `Live` 🌶️🌶️🌶️ 💴

- **主役**：AWS Sustainability API（A-8）、AWS Price List API
- **ハンズオン案**：同じ構成を東京・大阪・海外リージョンに置いた場合の「料金」「推計炭素排出量（LBM / MBM）」「水」を 1 枚の表にする。データのない部分（自分のワークロードのリージョン別排出量は、実際に動かさないと出ない）をどう推計するかも含めて誠実に書く。

### アルバム K：Out of Print（廃盤）とメタ

#### K-1. AWS のサービスは何年生きるのか — SDK 考古学による生存分析 ／ `Live` `Thought` 🌶️🌶️🌶️🌶️🌶️（AWS 費用なし）

- **素材**：§3 の Radar（botocore の Git 履歴）。何も契約せず、誰でも再現できる。
- **分析案**：サービスの「SDK 上の寿命」に対するカプラン・マイヤー推定、終了したサービスに共通する兆候（API 変更頻度の低下、リージョン展開の停止、What's New での言及の途絶）を特徴量にした簡単な予測モデル。
- **答えのない問い**：2024 年以降の「剪定期」は、AWS の戦略のどんな変化を示すのか。そして**ニッチなサービスを本番で採用するとき、何を見てリスクを見積もるべきか**（Deep Cuts 自身への問いでもある）。
- **注意**：「沈黙＝終了」ではない（EventBridge Scheduler のように完成していて変更不要な API もある）。誤った「死亡宣告」をしないよう、兆候は兆候として扱う。

#### K-2. 最古参サービスの終活 — SimpleDB ／ `Out of Print` 🌶️🌶️ 💴

- **素材**：2007 年公開の SimpleDB と、2026 年 3 月に追加された「エクスポートだけの v2 API」
- **ハンズオン案**：SimpleDB のドメインを作ってデータを入れ、v2 API でエクスポートし、DynamoDB へ移行する。Dynamo 論文（SOSP 2007）から DynamoDB へ至る歴史も添える。

#### K-3. 2026 年に消えたサービスの「次の住所」 ／ `Out of Print` 🌶️ 💴

- **素材**：IoT Events、IoT Analytics、Evidently、Panorama、SimSpace Weaver、FinSpace、Telco Network Builder（いずれも 2026 年に SDK から削除）
- **狙い**：それぞれの代替手段（例：Evidently → AppConfig のエクスペリメント（2026-06））を検証し、移行の落とし穴をまとめる。

#### K-4. Deep Cuts を本番で使う前に — ニッチサービス採用リスクの評価フレームワーク ／ `Thought` 🌶️🌶️

- **観点案**：API の活動量、リージョン展開、価格改定の有無、他サービスとの統合（CloudFormation・Config・CloudTrail 対応など）、データのエクスポート手段、代替手段への出口戦略。2026-10 に AWS Health に追加された `DescribeServiceLifecycle`（サポート終了日などを返す API）は公式の基礎データになり、SDK の兆候（K-1）と突き合わせられる。
- **狙い**：Deep Cuts が紹介するサービスに、毎回この「採用リスクカード」を付ける運用につなげる。
